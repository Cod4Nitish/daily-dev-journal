# Day 17 · 2026-11-20 · System design: rate limiting

_Category: System Design · Source: gemini_

Today I learned about the nuances of implementing rate limiting to protect backend services. While a fixed-window counter is simple to code, it suffers from edge-case spikes at the boundaries of time windows. I’ve shifted my focus to the token bucket algorithm, which elegantly allows for short bursts of traffic while enforcing a strict average rate over time.

For production-grade systems, accuracy is paramount. If precise enforcement is required, sliding-window logs or counters provide better granularity than fixed intervals. Crucially, I realized that rate limiting is a conversation with the client, not just a silent drop. When a limit is breached, I should always return an HTTP 429 status code accompanied by a `Retry-After` header to inform the client exactly when to resume requests.

```python
def is_allowed(user_id):
    bucket = redis.get(user_id)
    if bucket and bucket.tokens > 0:
        bucket.consume(1)
        return True
    return False
```

This approach creates a much smoother experience for developers consuming the API.
