# Day 16 · 2026-11-19 · System design: caching

_Category: System Design · Source: gemini_

Today I dove into the mechanics of caching, specifically the "cache-aside" pattern. It’s a clean approach: when a request comes in, I check the cache first. If it’s a miss, I fetch from the primary database and update the cache for subsequent reads. The biggest takeaway is that caching is less about performance and more about managing the invalidation story. Without a strategy, stale data is inevitable.

I implemented a basic TTL (Time-to-Live) to automate expiration, but I realized this introduces the "thundering herd" problem. If a high-traffic key expires, multiple concurrent requests might rush the database simultaneously. To mitigate this, I added a small amount of random jitter to the TTL. This ensures cache keys don't all expire at the exact same millisecond. 

```python
def get_data(key):
    val = cache.get(key)
    if val is None:
        val = db.query(key)
        cache.set(key, val, ttl=3600 + random.randint(0, 300))
    return val
```

It’s a simple change, but it significantly improves system resilience under load.
